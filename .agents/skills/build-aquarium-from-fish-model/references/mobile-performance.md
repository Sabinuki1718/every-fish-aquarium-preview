# スマホ向け軽量描画と起動負荷

スマホから開く水槽を制作・修正するときに読む。魚の形・模様・匹数、BGM、編集・保存を維持し、まず水面の描画回数、影、ピクセル数、プログラム数、読込み時のメモリーを減らす。素材を単色に戻したり魚を画像に置換したりして軽量化を完了しない。

## 画質を選び、実処理へ反映する

画面幅だけで判断しない。Android・iOSのUA、利用できるmobileヒント、タッチとcoarse pointerの組合せを使い、スマホでは軽量モードを初期値にする。画面回転だけで突然PC用へ戻さない。明示的な画質指定があれば優先する。設定表示だけ変えてPC用の描画を実行し続けない。

[画質と描画サイズの部品](../assets/mobile-quality.mjs)はThree.js等へ依存せず、次の出発点を返す。実際の端末・シーンに合わせて調整できる。

| 項目 | 軽量モードの出発点 | 通常モードの例 |
|---|---|---|
| 描画上限 | 30fps | 60fps |
| ピクセル比・長辺 | 比率最大1・長辺最大960px | 比率最大1.7 |
| 水面 | 波と法線・控えめなハイライトを持つ単一描画 | 動的反射・屈折を含む複数パス |
| 影・MSAA | シャドウマップとMSAAを省き、必要なら薄い接地影 | 画質と負荷に応じて使用 |
| 魚の画像 | 1024四方などの軽量用 | 原本相当の画像 |

```js
import {chooseAquariumQuality, aquariumDrawingSize} from './mobile-quality.mjs';
const quality=chooseAquariumQuality({
  userAgent:navigator.userAgent, userAgentMobile:navigator.userAgentData?.mobile,
  maxTouchPoints:navigator.maxTouchPoints, coarsePointer:matchMedia('(pointer:coarse)').matches,
  requestedQuality:new URLSearchParams(location.search).get('quality')??'auto',
});
const size=aquariumDrawingSize(quality,stage.clientWidth,stage.clientHeight,devicePixelRatio);
// 生成時のantialias、影の有効化、描画ループ、モデルURL選択もqualityへ接続する。
renderer.setPixelRatio(size.pixelRatio);
renderer.setSize(size.cssWidth,size.cssHeight,false);
```

部品はモデルの縮小や水面シェーダーの変更そのものを行わない。リサイズ時も描画サイズを再計算する。水槽全体が収まるカメラの調整は別に必要。

軽量側では、反射・屈折用のレンダーターゲットを作って毎フレーム描く処理を省く。単に反射率をゼロにしただけでは負荷が減らない。石の分割数・小礫の数も調整できるが、承認済みの大石の配置や色・材質は維持する。

## 同じ描画プログラムを共有する

個体番号・模様の位置・位相・ピボットなどをGLSL文字列に直接埋め込むと、似たプログラムが個体・部位ごとに作られ、起動時のコンパイルが膨らむ。実行時に変わる値はuniformへ移し、同じGLSLの間でプログラムを共有する。

- 体波の位相・振幅、胸鰭の左右・基部・位相は、個体ごとのuniformとして保持する。材質まで一律に共有して全個体が同時に動くようにしない。
- `customProgramCacheKey`にはシェーダー構造の差を表す情報だけを入れる。実際にGLSL・機能が違う材質を同じキーにしてはいけない。既存の模様補修・鰭・体波のフックを合成する。
- プログラム数だけでなく、影・反射・屈折を含む一フレーム全体のdraw callを測る。`renderer.info`が各render呼出しでリセットされる構成では、最後のパスだけの値を全体の値と報告しない。

## 起動時のメモリーを抑える

公開用は巨大なbase64入りJavaScriptを避け、小さな設定とGLB・画像のURLへ分ける。文字列・atob・ArrayBuffer・画像デコードが重なるピークを減らす。ローカルで通信不要という指定の成果物には必要な埋込み版を残し、公開用と区別する。

- 魚種・雌雄モデルの読込み、デコード、GPU転送を一度に集中させない。必要なら順次読み込み、フレームに分散する。
- 軽量GLBでは、まず内蔵画像の解像度を落とす。形状・UV・インデックス・法線・アニメーション・個体の模様を保つ。加工前後の形状バッファ等を比較する。透過が必要な鰭画像のアルファは保持する。
- JPEG/PNGの転送容量と、GPU上で展開された画像容量は別。RGBA相当では2048四方が約16MiB、1024四方が約4MiBで、mipmap等は別に加算される。GLBが小さくなったことだけでメモリー削減の検証にしない。
- 読み込んだ画像を使う複製材質が、同じ画像を重複してGPUへ載せていないか確認する。受け入れ済み原本を軽量版で上書きしない。

## ループと失敗時の扱い

描画上限はrequestAnimationFrame内の時刻で制御し、魚の移動・尾振りのdtも保つ。非表示タブでは描画を休止し、復帰時に長い経過時間で魚が飛ばないようにする。底面判定では、石を動かしたときに行列や衝突用の境界を更新し、支持点ごとに静止物の全行列を再計算する無駄を避ける。

初期化・モデル読込みの例外とWebGL context lossを扱い、待機表示が消えないままにしない。必要なら再読み込みの操作を出す。ブラウザーのタブ自体が終了した場合はページ内の例外処理では回復できない。

WebGL2コンテキストの作成失敗だけで、端末がWebGL2非対応だと断定しない。メモリー・GPUプロセス・ドライバー等も候補に含める。他の水槽が動くなら、使うエンジン・必須機能・負荷の差を比較する。軽量化とWebGL1対応は別の変更であり、軽量化しただけでWebGL1互換になったと説明しない。

## 比較検証と報告

- 通常・軽量の両方で、選択されたモード、実際のモデルURLと画像寸法、描画サイズ、プログラム数、全パスの描画回数を記録する。スマホで通常モデルも同時に取得していないかを見る。
- 雄雌や各魚種の匹数・模様・鰭・着底、BGMの再生と切替、タッチ操作、配置の保存と初期復帰、縦横回転を確認する。
- WebGLが作れない条件を模擬し、案内が出ることを確認する。これを実機でのクラッシュ再現と呼ばない。
- 画面幅だけ、UA・DPR・タッチの模擬、実機ブラウザー、X等のアプリ内ブラウザーを分けて扱う。PCのソフトウェアGPUで成功しても、実機Pixel等のドライバー互換性を確認したことにはならない。
- 公開を依頼されている場合は、同じサイトの既存IDと公開範囲を維持し、実装先の公開手順に従う。公開URLでも画質分岐・実ファイルの読込みを確認し、古い起動スクリプトとの混在を防ぐ。

今回のビワヨシノボリ水槽では、確認条件下でプログラム数171→14、全パスのdraw call約509→133となった。魚の形状は維持し、画像を2048→1024四方へ縮小した。これは採用手法の例であり、別の水槽の予算・実機のfps改善率・全端末での動作保証ではない。実機未確認ならその範囲を明記する。
